## 四、静态计数怎么算

| 动作 | `liveCount_` | `createdCount_` | `copiedCount_` | `destroyedCount_` | 编号 |
|---|---|---|---|---|---|
| 两参数 / 三参数构造 | +1 | +1 | — | — | 分配新编号 |
| 拷贝构造 `Assignment b = a;` | +1 | +1 | +1 | — | **分配新编号** |
| 拷贝赋值 `b = a;` | 不变 | 不变 | 不变 | — | **保持原编号** |
| 析构 | −1 | — | — | +1 | — |

两条容易写错的地方，都在代码里加了注释并写了断言：

1. **拷贝赋值不产生对象**，所以既不能 `++liveCount_`，也不能 `++createdCount_`，编号更不能改——
   否则“累计构造 ≠ 存活 + 已析构”，统计立刻失真。
2. **析构必须把 `this` 从存活清单里摘掉**，否则类级汇总会读到已销毁的对象（未定义行为）。

静态成员函数为什么不能写 `const`：它没有 `this`，本来就不属于某个对象；
在还没有任何对象时也能调用（`main` 第 0 部分就是演示这一点）。

## 五、完整配置输出：public getter 还是 friend？

需求是「完整配置」——除了名称、上限、是否要报告，还要看到两个内部标志
`titleConfigured_` / `maxBytesConfigured_` 和编号 `serial_`。两种做法：

**方案 A：补齐 public 查询接口**

```cpp
bool isTitleConfigured() const;
bool isMaxBytesConfigured() const;
```

- 优点：不破坏封装边界；调用方无需知道 `operator<<` 的存在；模板、泛型代码、后续 JSON 输出都好扩展。
- 缺点：为了“打印”把内部标志变成公开契约，一旦以后想合并这两个标志（例如换成 `ConfigState`），
  就变成破坏性改动；公开接口越多，越难维护不变式。

**方案 B：`friend std::ostream& operator<<(std::ostream&, const Assignment&)`**

- 优点：输出格式集中在一处，`printAll()` 直接复用；不必为打印新增任何 getter，
  对外接口只保留业务真正需要的 5 个查询函数。
- 缺点：友元是「白名单」，它绕过了封装；`friend` 不能继承、对模板不友好；
  一旦输出格式变多（文本 / JSON / CSV），一个 `operator<<` 会越写越臃肿。

**本工程的取舍：选 B，并限定它的边界。**

- `friend` 只用于「人读的文本快照」这一种用途，且实现只有 8 行；
- 通用查询仍走 public getter（`getTitle/getMaxBytes/getRequireReport/getSerial/isReady`），
  业务代码不需要认识 `operator<<`；
- 如果将来要输出多种格式，就把「取快照」抽成 `struct Snapshot { ... }` + `snapshot() const`，
  让各格式的输出函数都基于它——那时 `friend` 就可以退场。

这也是评审记录里第 6 条的处理结论（见 `REVIEW.md`）。

## 九、已知限制

1. **静态计数不是线程安全的**：`++liveCount_` 在多线程同时构造对象时会丢更新。
   若要在并发环境使用，需要改成 `std::atomic<int>`（或加锁），这超出本次作业范围，已在评审记录中登记。
2. **未实现移动语义**：类不持有堆资源，拷贝开销只有几个字段，暂时不需要 `= default` 的移动构造；
   但如果以后加入 `std::string` 之外的大对象，应补齐「五法则」。
3. **编号会随拷贝增长**：`nextSerial_` 只在构造（含拷贝）时递增，因此 `#4` 可能比 `#1` 晚创建，
   但编号本身不代表创建顺序的连续性——逻辑上它就是「第几次构造」。
